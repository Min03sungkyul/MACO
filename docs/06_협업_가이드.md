# 06. 협업 가이드 (Git·PR·병합·Docker, 초보자용)

> 4명이 한 저장소에서 같이 개발할 때 꼭 알아야 할 것만 모았다.
> 브랜치·커밋·PR의 공식 규칙은 [01_공통설계.md](01_공통설계.md) 2장, 화면 따라 하기는 [05_단계별_시작가이드.md](05_단계별_시작가이드.md) STEP 8~9를 본다.

## 1. 기본 그림

```
        GitHub (팀 공용 원본)
        ┌──────────────────────────────┐
        │  main  ← 완성본, 항상 실행됨      │
        │  feat/store-search  (민국)     │
        │  feat/exam-quiz     (동성)     │
        └──────────────────────────────┘
          ↑ push(올리기)      ↓ pull(받기)
   민국 PC     승준 PC     민하 PC     동성 PC
```

| 용어 | 쉬운 뜻 |
|---|---|
| **main** | 팀의 완성본. 언제 받아도 실행되는 상태여야 한다 |
| **브랜치** | 완성본을 복사한 **내 작업 공간**. 여기서 뭘 망쳐도 main은 안전하다 |
| **커밋** | 내 PC에 "여기까지 했음"을 저장. 아직 나만 본다 |
| **push** | 내 커밋을 GitHub의 **내 브랜치**에 올리기 |
| **pull** | GitHub의 최신 내용을 내 PC로 받기 |
| **병합(merge)** | 내 브랜치 내용을 main에 합치기 |

## 2. PR(Pull Request)이란

**PR = "제 브랜치 내용을 main에 합쳐 주세요"라는 요청서**다.

1. 내 브랜치를 push한다.
2. GitHub에서 PR을 만들고 무엇을 바꿨는지 설명을 쓴다 (PR 템플릿을 채운다).
3. 자동 검사(CI: 규칙 검사, 화면 빌드, 서버 테스트)가 돌고, **팀장 강민국에게 리뷰 요청이 자동으로 간다** (`.github/CODEOWNERS`).
4. 강민국이 보고 **승인**한다. (강민국 본인의 PR은 리뷰 없이 병합할 수 있다)
5. PR을 올린 사람이 **Squash merge**로 main에 합친다.

### 2-1. 리뷰 규칙

| PR을 올린 사람 | 리뷰어 | 병합 조건 |
|---|---|---|
| 주승준, 박민하, 이동성 | **강민국** (자동 지정) | CI 통과 + 강민국 승인 |
| 강민국 | 없음 | CI 통과 (필요하면 팀원에게 의견을 물어본다) |

- 팀원끼리 승인해도 병합되지 않는다. 강민국의 승인이 꼭 있어야 한다.
- 다른 담당 영역을 고친 PR은 그 담당자에게도 팀 채팅으로 알린다.
- 리뷰가 하루 넘게 밀리면 팀 채팅에서 강민국을 부른다. 금요일 통합(12/5, 12/12)·기능 동결(12/11) 전에는 PR을 미리 올린다.

PR이 없으면 누구 코드든 검사 없이 main에 바로 들어가고, 한 명의 실수로 4명 모두의 앱이 안 돈다. PR은 그걸 막는 **검문소**다.

## 3. 공통 부분은 누가 고치나

공통 부분마다 담당자가 따로 있고, **각자 자기 담당만 고친다.** 다른 사람은 정해진 메서드·부품을 불러 쓰기만 한다.

| 공통 부분 | 담당 | 다른 사람이 하는 일 |
|---|---|---|
| AI 모듈(`AiClient`), 규칙 파일·하네스 | 강민국 | `aiClient.run(...)`만 부른다 |
| 공통 UI(`components/ui`), 디자인 토큰 | 주승준 | 가져다 쓰고, 없는 부품은 요청한다 |
| `AppClock`, `XpService`, `SkillService`, 로그인, DB 마이그레이션 | 박민하 | 정해진 메서드만 부른다 |
| 문제 은행 CSV 형식, 오류 유형 | 이동성 | 형식대로 쓴다 |

### 3-1. 같이 고치면 어떻게 되나

Git이 막지는 않는다. 결과는 어디를 고쳤느냐에 따라 다르다.

| 상황 | 결과 |
|---|---|
| 서로 **다른 파일**을 고침 | ✅ 자동으로 합쳐진다 |
| 같은 파일, **다른 줄**을 고침 | ✅ 대부분 자동으로 합쳐진다 |
| 같은 파일의 **같은 줄**을 둘이 다르게 고침 | ⚠️ **충돌**. Git이 "둘 중 뭘 쓸까요?" 하고 멈추고 사람이 직접 골라야 한다 |

그래서 담당을 나눴다. **각자 자기 폴더만 고치면 충돌이 거의 생기지 않는다.**
남의 공통 부분에 고칠 게 생기면:

- 담당자에게 "이거 추가해 줘"라고 요청한다 (가장 좋음).
- 급하면 직접 고치되, PR 설명의 "다른 담당 영역 수정"에 적고 그 담당자에게도 알린다.

### 3-2. 공통 부분을 만들 때 주의할 점

1. **약속을 먼저 정하고 가짜 구현(스텁)을 먼저 올린다.** 메서드 모양(입력·출력)을 정하고 가짜 응답을 내는 버전을 먼저 main에 넣는다. 그래야 다른 팀원이 기다리지 않는다. 실제 구현은 그다음에 채운다.
2. **약속(메서드 이름·응답 모양)은 함부로 바꾸지 않는다.** 바꾸면 그걸 쓰는 모든 탭이 한꺼번에 깨진다. 꼭 바꿔야 하면 팀 채팅에서 먼저 합의한다. 공통 부분 PR은 강민국이 리뷰하고, 그 공통 부분을 쓰는 팀원에게도 알린다.
3. **API를 바꾸면 세 군데를 같이 고친다.** 서버 코드, `docs/03_API설계_초안.md`, `frontend/src/lib/types`. 하나라도 빠지면 화면과 서버가 서로 다른 모양을 기대한다.
4. **다른 패키지의 DB를 직접 건드리지 않는다.** 예: 스토어 코드에서 XP 테이블에 직접 쓰지 말고 `XpService`를 부른다.
5. **공통 UI에 부품이 없으면 내 탭 폴더에 임시로 만든다** (예: `components/store`). 그리고 주승준에게 공통화를 요청한다. `components/ui`를 직접 고치지 않는다.

## 4. 하루 작업 흐름

```
main 으로 이동 → pull → 새 브랜치 만들기 → 작업 → 커밋 → push → PR → 리뷰·승인 → Squash merge → 브랜치 삭제
```

1. `main`으로 이동 → **Pull** (최신 받기)
2. 새 브랜치 `feat/<탭>-<내용>` 만들기 (main에서 바로 작업하지 않는다)
3. 작업 → 커밋 → 내 브랜치를 **Push**
4. GitHub에서 **PR 만들기** → 강민국에게 리뷰 요청이 자동으로 간다
5. 승인 후 **Squash merge** → **브랜치 삭제** → 1번으로 (강민국 본인 PR은 승인 없이 병합)

### 4-1. 커밋하기 전에

- 바뀐 파일 목록(`git status` 또는 GitHub Desktop의 Changes)을 꼭 본다. `.env`, `.claude/settings.local.json` 같은 개인 파일이 섞여 있으면 커밋하지 않는다.
- 내 담당이 아닌 파일이 바뀌어 있으면 이유가 있는지 확인한다.
- 커밋 메시지는 `feat(store): 가게 검색 API 추가`처럼 `종류(탭): 한국어 설명`.
- 검사를 돌린다: `node scripts/check-rules.mjs` (루트), `./gradlew test` (backend), `npm run lint`·`npm run build` (frontend).
- 작게 커밋한다. PR 하나에 기능 하나, 400줄 이하 권장.

### 4-2. pull 받은 뒤에

- `frontend/package.json`이 바뀌었으면 `npm install`을 다시 한다.
- 백엔드 라이브러리는 Gradle이 알아서 받는다. 새 DB 마이그레이션은 서버를 실행할 때 자동 적용된다.
- `.env.example`에 새 이름이 생겼으면 내 `.env`에도 추가한다 (값은 팀 비공개 채팅으로 받는다).

### 4-3. 충돌이 났을 때

- **PR을 올린 사람**이 해결한다. 최신 main을 내 브랜치에 합친 뒤 충돌 부분을 고쳐 다시 push한다.
- 모르면 혼자 지우지 말고 팀 채팅에 물어본다.
- **force push, `git reset --hard`는 하지 않는다.** 팀원 작업이 날아갈 수 있다.

### 4-4. 병합된 브랜치는 다시 쓰지 않는다

Squash merge는 브랜치의 커밋을 하나로 합쳐 main에 넣는다. 병합된 브랜치에 계속 커밋하면 다음 PR에 이미 들어간 변경이 또 섞여 보인다.
**병합 후에는 브랜치를 지우고, 최신 main에서 새 브랜치를 만든다.**

## 5. 순서가 중요한가

**push 순서는 상관없다.** 각자 **자기 브랜치**에 올리기 때문에 서로 덮어쓰지 않는다.

중요한 순서는 두 가지다.

**① 작업 시작 전에 꼭 pull 먼저.**
예전 main에서 브랜치를 만들면 남들이 이미 바꾼 내용을 모른 채 작업하게 되고, 나중에 충돌이 커진다.

**② 병합(merge) 순서.**

- 먼저 병합한 사람은 편하고, 나중에 병합하는 사람이 충돌을 해결한다.
- **다른 사람이 쓰는 것(공통 모듈 스텁)을 먼저 병합한다.**
  예: 박민하의 `XpService` 스텁이 main에 들어와야 이동성의 시험 기능이 그걸 쓸 수 있다.
  ```
  공통 모듈 스텁 PR 병합 → 다들 main pull → 각 탭에서 사용
  ```
- **DB 마이그레이션 번호**가 겹치면(둘 다 `V5__`) 나중에 병합하는 사람이 다음 번호로 바꾼다.

## 6. 자동으로 최신화되나

**아니다. 자동인 것과 직접 해야 하는 것이 나뉜다.**

| 상황 | 자동? | 설명 |
|---|---|---|
| 팀원 PR이 병합되면 GitHub의 main | ✅ 자동 | GitHub 서버의 main은 바로 바뀐다 |
| 내 PC의 main | ❌ 직접 | **pull**해야 내 PC에 들어온다 |
| 내가 작업 중인 브랜치 | ❌ 직접 | 저절로 안 들어온다. 최신 main을 내 브랜치로 합쳐야 한다 (GitHub Desktop: Branch → Update from main) |
| 내 로컬 DB 테이블 | 🔶 반자동 | pull 후 서버를 실행하면 Flyway가 새 마이그레이션을 적용한다 |
| 내 로컬 DB 데이터 | ❌ 공유 안 됨 | 각자 PC에 따로 있다 (7장) |
| PR 검사 | ✅ 자동 | PR을 올리면 CI가 규칙 검사·화면 빌드·서버 테스트를 돌린다 |
| 리뷰어 지정 | ✅ 자동 | 팀원 PR은 강민국에게 리뷰 요청이 간다 (CODEOWNERS) |

- **push는 내 브랜치에만 한다.** main은 직접 push하지 않고 PR 병합으로만 바뀐다 (저장소 보호 설정).
- 누가 병합했다고 하면 → 각자 main에서 pull.
- 내 작업이 며칠 걸리면 → **매일 아침 최신 main을 내 브랜치로 합친다.** 마지막에 충돌이 한꺼번에 터지지 않는다.

## 7. Docker가 하는 일

이 프로젝트에서 Docker는 **로컬 MySQL DB를 띄우는 일 하나만** 한다. `docker-compose.yml`에는 `mysql:8.4` 하나만 있다. 백엔드·프론트는 Docker 없이 `./gradlew bootRun`, `npm run dev`로 직접 실행한다.

**왜 쓰나:** MySQL을 각자 설치하면 버전·문자셋(한글 깨짐)·시간대·비밀번호가 사람마다 달라진다. Docker를 쓰면 명령 한 줄로 4명이 **똑같은 설정의 DB**(MySQL 8.4, utf8mb4, Asia/Seoul, 계정 `maco`/`maco_local`)를 갖는다.

DB 켜기 (루트에서):

```bash
docker compose up -d
```

켜졌는지 확인 (`maco-mysql`이 보이면 성공):

```bash
docker ps
```

DB 끄기 (데이터는 남는다):

```bash
docker compose down
```

### 7-1. 헷갈리기 쉬운 것

- ⚠️ **DB 데이터는 팀원끼리 공유되지 않는다.** 각자 PC 안에 각자의 DB가 있다. 내가 넣은 테스트 데이터는 다른 팀원에게 안 보인다.
- **테이블 구조는 코드로 공유된다.** Flyway 파일(`V1__...sql`)이 Git에 있고, 서버를 실행하면 아직 적용 안 된 파일이 자동으로 실행된다.
- **기본 데이터도 자동이다.** 문제 은행 CSV와 예시 계정은 서버가 `local` 프로필로 처음 시작할 때 자동으로 넣는다.
- **컴퓨터를 켤 때마다 Docker Desktop을 먼저 실행**해야 `docker compose`가 동작한다.
- PC에 MySQL을 따로 설치했다면 3306 포트가 겹쳐 실행이 안 될 수 있다.

### 7-2. DB가 꼬였을 때 처음부터 다시 만들기

```bash
docker compose down -v
```

`-v`를 붙이면 **내 로컬 DB 데이터가 전부 지워진다.** 다음 서버 실행 때 테이블과 기본 데이터가 다시 생긴다.
아직 병합 전인 내 마이그레이션 파일을 고쳐서 Flyway 오류(checksum mismatch)가 날 때 쓴다.

## 8. 팀원 공유용 요약: 협업 규칙 7가지

1. **main에서 직접 작업하지 않기.** 항상 `feat/<탭>-<내용>` 브랜치를 새로 만들어서 작업한다.
2. **작업 시작 전에 main pull 먼저.** 아침에 한 번, 누가 병합했다고 하면 또 한 번.
3. **내 담당 폴더만 고치기.** 남의 공통 부분(UI, XP, AI 등)은 담당자에게 요청한다. 직접 고쳤으면 PR에 꼭 적는다.
4. **PR은 작게, 자주.** 기능 하나에 PR 하나. 크면 리뷰도 어렵고 충돌도 커진다. 리뷰어는 강민국으로 자동 지정되고, 강민국이 승인해야 병합된다.
5. **충돌은 PR 올린 사람이 해결.** 모르면 혼자 지우지 말고 팀 채팅에 물어본다. **force push, `reset --hard` 금지.**
6. **커밋 전에 바뀐 파일 목록 확인.** `.env`(비밀번호·키)가 섞여 있으면 절대 커밋하지 않는다.
7. **병합된 브랜치는 지우고 새로 만들기.** 병합이 끝난 브랜치에 계속 커밋하면 다음 PR이 꼬인다.
