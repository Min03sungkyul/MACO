# 01. 공통 설계 (프로토타입 기초)

> 기준: [MACO 서비스 기획서](MACO_서비스기획서.md) 9장(탭), 10장(기술), 12-1(프로토타입 범위), 13장(역할).
> 이 문서는 **첫 주(11/27~12/2)에 함께 정하고 고정**한다. 바꾸려면 팀 채팅에 먼저 올리고 합의한다.

## 0. 역할 한눈에 보기

| 담당 | 탭 (화면 + 서버) | 모두가 쓰는 공통 부분 |
|---|---|---|
| 강민국 (팀장) | 🏪 내 가게 | **AI 모듈**(AiClient), 시연 AI 응답 저장, 금요일 통합, 발표 |
| 주승준 | 📚 트레이닝 | **공통 UI 컴포넌트**·디자인 토큰, 프론트 뼈대 |
| 박민하 | 🏆 랭킹 + 👤 내 정보 | **공통 기반**: 백엔드 뼈대, 로그인·JWT, DB 마이그레이션, API 규칙, **XP 적립**, **Elo 출제 엔진**, 가상 날짜, 배포 |
| 이동성 | 📝 시험 | **문제 은행 형식·오류 유형 사전**, 문제 60개 검수, 상황극 시나리오·루브릭 |

공통 부분은 "약속(인터페이스)"을 먼저 정하고, 담당자가 만든다. 다른 사람은 약속대로 불러 쓰기만 한다. 담당자가 다 만들기 전에는 **가짜 구현(스텁)**을 먼저 올려 다른 사람이 막히지 않게 한다.

## 1. 저장소

- GitHub에 **비공개 저장소 하나** (`maco`)를 만든다. 팀장이 만들고 3명을 초대한다. 졸업 후 공개 여부는 나중에 정한다.
- 화면·서버·문서를 한 저장소에 둔다(모노레포). 4명이 탭 단위로 화면과 서버를 같이 고치기 때문에 저장소가 하나여야 PR 하나로 끝난다.
- 저장소는 **영문 경로**에 받는다 (예: `C:\dev\maco`).

```
maco/
├─ frontend/                Next.js (TypeScript) — Vercel 배포
├─ backend/                 Spring Boot (Java 21, Gradle)
├─ content/                 문제 은행·개념 카드·오류 유형 사전 (CSV, 이동성 관리)
├─ docs/                    설계 문서 (이 폴더의 개발/ 문서를 옮겨 옴)
├─ docker-compose.yml       로컬 MySQL (+ 배포용은 docker-compose.prod.yml)
├─ .env.example             필요한 환경 변수 이름만 (값 없음)

```

- 화면 기준: 모바일 폭 **375~430px**, 큰 화면에서는 가운데 480px 칸으로 보여 준다.

```
├─ auth/        로그인·회원가입·소셜 로그인                     박민하
├─ user/        사용자, 설정, 모드, 지역                        박민하
├─ xp/          XP 적립, 일일 목표, 스트릭, 배지                 박민하
├─ skill/       Elo 엔진, 출제, 풀이 기록(attempt), 학습자 모델   박민하
├─ content/     문제·개념 카드·오류 유형·연습 가게 읽기, CSV 적재  이동성 (적재기는 박민하와 함께)
├─ training/    유닛 경로, 레슨, 배치 테스트                     주승준
├─ exam/        쪽지시험, 오답 노트, 상황극, 유닛 시험             이동성
├─ store/       가게, 캡처 진단, 관문, 틀린 곳 찾기, 미션, QR      강민국
├─ ai/          AiClient, 프롬프트, 캐시, 로그, 저장 응답          강민국
├─ ranking/     주간 리그, 지역 랭킹                             박민하
├─ report/      학습 기록, 성장 리포트                           박민하
└─ demo/        날짜 넘기기, 시연 초기화                          박민하
```

- 패키지 안은 `controller / service / repository / domain / dto` 순서로 나눈다.
- DB 접근: Spring Data JPA. 복잡한 집계(랭킹)만 네이티브 쿼리를 허용한다.
- DB 구조 변경은 **Flyway**만 사용한다 (`backend/src/main/resources/db/migration/V{번호}__{설명}.sql`). 엔티티 자동 생성(`ddl-auto=update`)은 끈다.
- API 문서: springdoc-openapi로 `/swagger-ui`를 자동 생성한다. 프론트 담당은 이 화면을 보고 연결한다.
- 다른 패키지의 **service만 호출**한다. 다른 패키지의 repository나 테이블을 직접 건드리지 않는다.

## 2. 브랜치·커밋·PR

| 항목 | 규칙 |
|---|---|
| 기본 브랜치 | `main` 하나. **항상 실행되는 상태**를 유지. 직접 푸시 금지(보호 설정) |
| 작업 브랜치 | `feat/<탭>-<내용>` · `fix/<탭>-<내용>` · `docs/<내용>` · `chore/<내용>` (예: `feat/exam-daily-quiz`, `feat/common-xp-api`) |
| 탭 이름 | `common` `training` `exam` `store` `ranking` `me` `content` `ai` |
| 커밋 메시지 | `feat(exam): 쪽지시험 채점 API 추가`처럼 `종류(탭): 한국어 설명` |
| PR | 작은 단위로 하루 1개 이상. 설명에 "무엇을 / 어떻게 확인했나 / 화면 캡처" |
| 리뷰 | 짝 리뷰 1명 승인 후 병합. 짝: **트레이닝 ↔ 시험**, **랭킹 ↔ 내 가게**. 공통 부분 PR은 담당자 + 1명 |
| 병합 방식 | Squash merge (커밋 하나로 합쳐 병합) |
| 충돌 | 받는 쪽이 아니라 **PR을 올린 사람**이 `main`을 받아 해결 |
| DB 마이그레이션 | 번호가 겹치면 나중에 병합하는 사람이 다음 번호로 바꾼다. 이미 병합된 마이그레이션 파일은 고치지 않고 새 파일로 고친다 |

GitHub Desktop 기준 하루 흐름:
1. `main`으로 이동 → **Fetch / Pull** (최신 받기)
2. **New branch** → `feat/...` 만들기
3. 작업 → 커밋 → **Publish branch / Push**
4. **Create Pull Request** → 짝에게 리뷰 요청
5. 승인 후 병합 → 브랜치 삭제 → 1번으로

### 3-1. 환경 변수

## 4. API 규칙

| 항목 | 규칙 |
|---|---|
| 주소 | `/api/v1/...`, 명사·복수형, 소문자-하이픈 (예: `/api/v1/wrong-notes`) |
| 인증 | `Authorization: Bearer <JWT>`. 로그인·회원가입·지역 목록만 인증 없이 허용 |
| 형식 | JSON, 필드는 camelCase. DB 컬럼은 snake_case |
| 날짜 | `2026-12-16`, 시각은 `2026-12-16T09:30:00+09:00`. 시간대는 **Asia/Seoul** 고정 |
| 성공 응답 | `{ "data": { ... } }` |
| 실패 응답 | `{ "error": { "code": "QUIZ_ALREADY_SUBMITTED", "message": "오늘 쪽지시험은 이미 제출했어요" } }` |
| HTTP 상태 | 200 성공, 201 생성, 400 입력 오류, 401 로그인 필요, 403 권한 없음, 404 없음, 409 중복·상태 충돌, 500 서버 오류 |
| 에러 코드 | `대문자_스네이크`, 탭 접두어 없이 뜻으로 (`ITEM_NOT_FOUND`, `XP_DAILY_CAP`) |
| 목록 | `?page=0&size=20`, 응답 `{ "data": { "items": [...], "page": 0, "hasNext": true } }` |
| XP가 생기는 응답 | 응답 안에 **`xp` 필드(XpResult)**를 함께 돌려준다. 프론트는 이것만 보고 XP 알림·목표 링을 갱신한다 |

## 5. 공통 모듈 약속

### 5-1. 가상 날짜 — `AppClock` (박민하)

시연에서 "4주 넘기기"를 하려면 모든 "오늘"이 바뀌어야 한다.

- 서버 어디에서도 `LocalDate.now()` / `LocalDateTime.now()`를 직접 쓰지 않는다. **`appClock.today(userId)`, `appClock.now(userId)`**만 쓴다.
- 오늘 = 실제 오늘 + `users.demo_day_offset`. 시연 계정만 offset을 바꿀 수 있다.
- 한 주는 **월요일 시작**(리그 초기화 기준).
- 프론트는 날짜를 스스로 계산하지 않고 서버가 준 `today`를 쓴다.

### 5-2. XP 적립 — `XpService` (박민하)

모든 탭은 XP를 직접 쓰지 않고 이 서비스만 부른다.

```java
XpResult award(Long userId, XpReason reason, String sourceKey);
XpResult awardScore(Long userId, XpReason reason, String sourceKey, int score0to100); // 상황극용
```

| XpReason | XP | 부르는 곳 |
|---|---|---|
| `PRACTICE_CORRECT` / `PRACTICE_WRONG` | 10 / 2 | 연습 문제 (skill 엔진이 대신 부름) |
| `LESSON_COMPLETE` | 10 | 트레이닝 |
| `QUIZ_CORRECT` / `QUIZ_PERFECT` | 4 / +10 | 시험 |
| `ROLEPLAY` | 루브릭 0~100 → 0~20 | 시험 |
| `SPOT_FOUND` | 5 | 내 가게 |
| `UNIT_TEST_PASS` | 30 | 시험 (P1) |
| `MISSION_PASS` | 50 | 내 가게 (첨삭 통과 시) |
| `STREAK_7` | 20 | XP 서비스가 스스로 |

- `sourceKey`(예: `quiz:123:item:45`)가 같으면 **두 번 주지 않는다**.
- 같은 문제를 같은 날 다시 풀면 절반, 세 번째부터 0. 하루 상한 300 XP. 이 계산은 서비스 안에서만 한다.
- 돌려주는 값:

```json
{ "gained": 10, "todayXp": 48, "goalXp": 60, "goalAchievedNow": false,
  "streakDays": 3, "levelUps": [ { "skill": "PHOTO", "from": 1, "to": 2 } ] }
```

### 5-3. 학습자 모델·Elo 출제 — `SkillService` (박민하)

트레이닝(레슨·배치 테스트)과 시험(쪽지시험·오답 노트)이 함께 쓴다.

```java
List<ItemDto> pick(Long userId, PickRequest req);      // skills, count, context, includeReview
AttemptResult record(Long userId, AttemptRequest req); // itemId, answer, context, sessionId, elapsedMs
```

- 맞힐 확률 `p = 1 / (1 + e^-(θ - d))` (θ: 사용자 스킬 실력, d: 문제 난이도)
- 갱신: `θ ← θ + K_u (r − p)`, `d ← d − K_i (r − p)` (r: 맞으면 1, 틀리면 0)
- 출발값(가정): θ 시작 0(배치 테스트로 조정), d는 난이도 초깃값 1~5를 −2~+2로 환산, `K_u = 0.4 / (1 + 0.05·푼 문제 수)`, `K_i = 0.1`
- 출제: p가 **0.7**에 가까운 문제 우선 + 약점 오류 유형 문제 + 복습 날짜가 된 오답 문제 섞기 (레슨 7문제 중 복습 2개 가정)
- 스킬 레벨(가정): θ < −1 → Lv1, < −0.3 → Lv2, < 0.3 → Lv3, < 1 → Lv4, 이상 → Lv5
- 채점: 고르기·상황 판단·틀린 곳 찾기는 규칙으로. 고쳐 쓰기는 AI 채점 점수 70 이상이면 정답으로 기록
- `record`는 attempt 저장 → θ·d 갱신 → 오답이면 오답 노트·복습 날짜 등록 → XP 적립까지 한 번에 처리하고 결과를 돌려준다:

```json
{ "correct": false, "answer": "B", "errorType": "PHOTO_DARK",
  "explanation": "어두운 사진은 맛이 없어 보여요", "principleCardId": 12,
  "xp": { "...": "XpResult" } }
```

### 5-4. AI 모듈 — `AiClient` (강민국)

AI 회사 SDK·API는 **`ai` 패키지 밖에서 절대 직접 부르지 않는다.** 나중에 모델을 바꾸거나 로컬 모델로 옮겨도 이 패키지만 고치면 된다.

```java
<T> AiResult<T> run(AiTask task, Object input, Class<T> outputType);
```

| AiTask | 쓰는 탭 | 입력 → 출력 |
|---|---|---|
| `CAPTURE_READ_PLACE` / `CAPTURE_READ_INSTA` | 내 가게 | 캡처 이미지 → 항목값 JSON (영업시간, 리뷰 수 …) |
| `REWRITE_GRADE` | 트레이닝 | 문제 + 사용자 문장 + 루브릭 → 항목별 점수, 고칠 점 1개 |
| `EXPLAIN_WRONG` | 트레이닝·시험 | 문제 + 고른 답 + 오류 유형 → 설명 2~3문장 |
| `ROLEPLAY_TURN` | 시험 | 시나리오 + 대화 기록 → 손님의 다음 말 |
| `ROLEPLAY_REPORT` | 시험 | 대화 전체 + 루브릭 → 점수, 잘한 점, 고칠 문장 3개 |
| `MISSION_FEEDBACK` | 내 가게 | 제출물(사진·문구) + 미션 기준 → 항목별 채점, 통과 여부, 고칠 점 |
| `WEEKLY_COACH` (P1) | 시험 | 한 주 기록 요약 → 코칭 카드 문장 |

```json
{ "ok": true, "source": "LIVE | CACHE | RECORDED | FALLBACK", "data": { }, "latencyMs": 1830 }
```

- 프롬프트는 `backend/src/main/resources/prompts/<task>.md` 파일로 관리한다 (코드에 문장을 박지 않음).
- 출력은 JSON으로 받아 형식을 검사하고, 틀리면 1번만 다시 요청, 그래도 틀리면 `FALLBACK`(미리 쓴 규칙 문장·체크리스트)을 돌려준다. **부르는 쪽은 `FALLBACK`일 때도 화면이 동작하게 만든다.**
- 같은 입력은 `ai_cache`에서 재사용, 모든 호출은 `ai_log`에 토큰·비용·시간을 남긴다.
- `AI_MODE=recorded`면 저장된 응답만 쓴다 (시연·키 없는 팀원용).
- 이미지는 보내기 전에 긴 변 1568px 이하로 줄인다. 사용자 이름·연락처는 프롬프트에 넣지 않는다.
- 담당이 실제 구현을 마치기 전, **첫 주에 `recorded` 모드 스텁을 먼저 올린다.**

### 5-6. 문제 은행 형식·오류 유형 사전 (이동성)

MVP는 기획서 E5대로 **스프레드시트로 쓰고 CSV로 내보내 `content/`에 커밋** → 서버 시작 시 DB에 넣는다. 관리자 화면은 만들지 않는다.

| 파일 | 한 줄 = | 주요 열 |
|---|---|---|
| `skills.csv` | 스킬 | code, name, gate, unit_order |
| `concept_cards.csv` | 개념 카드 | id, skill, level, title, body, evidence |
| `lessons.csv` | 유닛 경로의 레슨 | id, skill, level, seq, title, concept_card_id |
| `error_types.csv` | 오류 유형 | code, skill, name, description, fix_tip, evidence |
| `items.csv` | 문제 | code, skill, type, kind, mode_scope, store_type, init_difficulty(1~5), prompt, media, choice_a, choice_b, choice_c, choice_d, answer, error_a~error_d, explanation, concept_card_id |
| `hotspots.csv` | 틀린 곳 찾기 영역 | item_code 또는 screen_code, x, y, w, h (이미지 대비 %), error_type |
| `rubrics.csv` | 고쳐 쓰기·상황극·미션 채점 기준 | code, criterion, weight, description |
| `roleplay_scenarios.csv` | 상황극 | code, skill, persona, opening_line, max_turns, rubric_code, mode_scope |
| `practice_stores.csv` | 연습 가게 | code, store_type, name, place_image, insta_image, menu, reviews |

- 스킬 코드: `INFO`(기본 정보·찾게), `PHOTO`(보여 주기·찾게), `REVIEW`(리뷰·믿게), `COPY`(소개 문구·믿게), `PROMO`(알리기·알리게), `ADS`(광고와 숫자·알리게). **프로토타입은 PHOTO, REVIEW 두 스킬.**
- 문제 코드: `<스킬>-<유형>-<번호>` (예: `PHOTO-CHOICE2-007`). 한 번 정한 코드는 바꾸지 않는다(풀이 기록이 코드로 연결됨).
- 틀린 보기마다 **오류 유형을 하나씩** 붙인다. 약점 리포트·오답 설명·개인별 코칭이 모두 이 값으로 움직인다.
- 오류 유형 초안 (이동성이 확정):

| 스킬 | 코드 예시 |
|---|---|
| PHOTO | `PHOTO_DARK`(어두움), `PHOTO_BLUR`(흔들림), `PHOTO_NO_HERO`(주인공 없음), `PHOTO_CLUTTER`(배경 지저분), `PHOTO_ORDER`(대표 사진 순서) |
| REVIEW | `REPLY_NEEDED_MISSED`(답글이 필요한 리뷰를 놓침), `REPLY_NO_EMPATHY`(공감 없음), `REPLY_NO_APOLOGY`(사과 없음), `REPLY_NO_FIX`(개선 약속 없음), `REPLY_NO_REVISIT`(재방문 제안 없음), `REPLY_DEFENSIVE`(변명·반박), `REPLY_TEMPLATE`(복사한 듯한 답글) |
| 공통 | `COPY_NO_PRICE`(가격 누락), `COPY_NO_CTA`(행동 유도 없음) |
